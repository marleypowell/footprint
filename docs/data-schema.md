# Raw dataset: one person's work across an org

Generated by `footprint` (the repo's `README.md` explains how to re-run it). The data is
raw on purpose: nothing is summarised, deduplicated or filtered beyond "involves the user". Every
record says *how* it involves the user, so the aggregation phase decides what counts.

The field names are tool-neutral. `index.json` -> `sources` records which code host, catalog and
issue tracker produced the data (today `github`, `backstage`, `jira`). Where a record keeps a
tool's own data as written (the raw catalog `entity`, `kind`, `source_repo_basis`), that is noted.

Start at `index.json`. It lists every repo with activity, with explicit paths to its files and
headline counts. Use the index rather than globbing: a repo whose name starts with a dot (for
example `.github-private`) becomes a dot-directory, which `*` skips.

## Layout

```
index.json                    entry point: sources, totals, one entry per repo (sorted by activity)
README.md                     this file
org/
  repos.json                  every repo in the org (code host metadata), including ones with no activity
  identities.json             every author/committer/co-author identity resembling the user, with counts
  issue_projects.json         the issue tracker's projects (key -> name), when known, for decoding issue_keys
  verification.json           cross-check against the code host's own attribution (see Completeness)
catalog/
  entities.jsonl              every catalog entity found on any default branch in the org
  files/<repo>/<path>         the raw descriptor files those entities came from
  parse_errors.json           descriptor files that could not be parsed
repos/<repo>/
  project.json                what the repo is: code host metadata, catalog entities + context, docs, layout
  docs/<path>                 README / CLAUDE.md / AGENTS.md / docs index / package.json from the default branch
  commits.jsonl               the user's commits (one JSON object per line, oldest first)
  prs.jsonl                   pull requests authored by the user (one per line, by number)
```

## commits.jsonl

A commit is included if the user is its **author** or **committer**, if a `Co-authored-by:` trailer
names them, or if it is part of, or landed, a **PR the user authored** (`pr-author`; this is how
Claude Code / Copilot agent commits and colleagues' pushes to the user's PRs get in). Matching is by
email (case-insensitive; config in `index.json` -> `identity`), and by exact name only for the full
names listed there. Commits come from **every ref**: the default branch, all branches, tags, and the
head of every change request (mirrored as `refs/pull/<n>/head`, whatever the code host calls them;
GitHub keeps these after branches are deleted). Because of this, the original commits behind
squash-merged PRs are present as well as the squash commit.

| field | meaning |
|---|---|
| `repo`, `sha`, `url` | identity of the commit; `url` is its page on the code host |
| `roles` | subset of `author`, `committer`, `co-author`, `pr-author`: how the user is involved |
| `matched_by` | per role, whether the match was on `email` or `name` (`authored_pr` for `pr-author`) |
| `in_user_prs` | numbers of PRs authored by the user that contain this commit (joins to `prs.jsonl`) |
| `merge_commit_for_user_prs` | numbers of the user's PRs that this commit landed (squash or merge commit = the PR's `merge_commit_sha`) |
| `author`, `committer` | `{name, email, date}`; dates are ISO 8601 in the committer's local offset |
| `co_authors` | every `Co-authored-by:` trailer (anyone, not just the user; includes AI agents) |
| `subject`, `body`, `message` | first line, the rest (the "description"), and the full raw message |
| `parents`, `is_merge` | parent shas; merges have `stats: null` and no `files` (no diff is computed) |
| `on_default_branch` | reachable from the repo's default branch (i.e. landed) |
| `branches`, `pull_request_refs`, `tags` | for commits **not** on the default branch only: which other refs contain it (capped at 50 each; `containing_ref_counts` has the true totals). The lowest PR number is usually the PR that introduced the commit |
| `pr_numbers_in_message` | change-request numbers the message says it merged, by the code host's conventions (GitHub: `Title (#123)` squash subjects, `Merge pull request #123`) |
| `azure_devops_pr_numbers_in_message` | pre-migration `Merged PR 12345:` numbers (Azure DevOps; not the current host's PRs) |
| `issue_keys` | issue tracker keys from the message and containing branch names, restricted to the tracker's real projects (`org/issue_projects.json` plus extras in config) |
| `patch_id` | `git patch-id --stable`: equal for the same change rebased/cherry-picked onto another base. Null for merges/empty commits |
| `stats` | `{files, additions, deletions, binary_files}` for the whole commit |
| `files` | `[{path, old_path?, status, similarity?, additions, deletions, binary}]`; status is A/M/D/R/T. Capped at 5000 (`files_truncated`) |

Things the aggregation phase will want to handle:

- **Duplicates.** A rebased or cherry-picked change appears once per copy (same `patch_id`, different `sha`).
  A squash-merged PR appears as its original commits (on `refs/pull/<n>/head`, not on the default branch)
  **and** as the squash commit on the default branch (`pr_numbers_in_message` = `[n]`).
- **Roles that are not really "my work".** `committer`-only commits are rebases or cherry-picks of other
  people's commits. In repos migrated from Azure DevOps they are also PR completions: the author is a bot
  such as `Project Collection Build Service`, typically for dependency bumps the user merged.
  `co-author`-only commits are colleagues' squash merges that included a commit by the user, or agent
  commits (`copilot-swe-agent[bot]`) crediting the user. `pr-author`-only commits were authored by someone
  else inside the user's PR: an agent such as `Claude <noreply@anthropic.com>` (AI-assisted work driven by
  the user), or a colleague pushing to the PR. Check `author` to tell them apart.
- **Merge commits** (`is_merge`) include web-UI "Merge pull request" commits made by clicking Merge.
- **Author-only** commits are usually committed by the code host itself (a web-UI squash merge or edit).
- **Pre-migration history.** Repos migrated from another host (e.g. Azure DevOps) with their history keep
  their older commits, which can predate the repo on the current host (`index.json` ->
  `first_commit_in_repo` vs `created_at`).

## prs.jsonl

Pull requests (merge requests, on GitLab) whose author is the user, in any state.

| field | meaning |
|---|---|
| `repo`, `number`, `url`, `title`, `body` | the PR and its description (markdown) |
| `state`, `is_draft`, `created_at`, `updated_at`, `closed_at`, `merged_at` | lifecycle |
| `author`, `merged_by`, `base_ref`, `head_ref`, `head_sha`, `merge_commit_sha` | refs; `merge_commit_sha` is the squash/merge commit on the base branch |
| `additions`, `deletions`, `changed_files` | size of the PR |
| `review_decision`, `reviews`, `review_count`, `requested_reviewers`, `comment_count` | review activity on the PR |
| `labels`, `assignees`, `closing_issues` | metadata |
| `commits` | every commit in the PR (`sha`, `headline`, author name/email/login). Joins to `commits.jsonl` by `sha`; commits by other people (or agents) in the user's PRs are listed here even when they are not in `commits.jsonl` |
| `files` | every changed path with `additions`, `deletions`, `change_type` |
| `issue_keys` | from title, body and head branch name |

## project.json (what each project is)

| field | meaning |
|---|---|
| `code_host` | the repo's code host metadata (the `org/repos.json` record): description, topics, languages (bytes), visibility, archived, created/pushed dates |
| `history` | first commit date in the repo, root commit count, commit/branch/tag/PR-ref counts in the mirror |
| `catalog.entities` | catalog entities describing this repo (records as in `catalog/entities.jsonl`), systems first. Monorepos have one per app; `path` shows which directory it describes |
| `catalog.context` | entities those are part of, resolved transitively through `part_of`: the system and its domain, owner groups, parent components. `null` = referenced but not defined in any descriptor (e.g. groups synced from the IdP) |
| `docs` | files saved under `docs/`: root README, CLAUDE.md, AGENTS.md, copilot instructions, docs index, mkdocs.yml, package.json, plus READMEs next to each catalog descriptor |
| `tree_top` | the repo's directory layout to depth 2: a fallback for undocumented repos |
| `activity` | headline counts and first/last dates computed from `commits.jsonl` and `prs.jsonl` (`issue_keys` is a count) |

For repos with no catalog entity and no description, `docs/` and `tree_top` are the only description.

## catalog/entities.jsonl

One line per entity, tool-neutral fields first:

| field | meaning |
|---|---|
| `ref` | the entity's id in the catalog (Backstage: `kind:namespace/name`) |
| `kind` | the catalog's own kind, as written (Backstage: `Component`, `System`, ...) |
| `category` | the neutral class: `system`, `component`, `api`, `resource`, `domain`, `group` or `other` (bookkeeping such as locations and templates) |
| `title`, `description`, `type` | as declared; `null` when absent. `type` is e.g. `service`, `website`, `library` |
| `found_in_repo`, `path`, `doc_index` | where the descriptor lives, and its position among the file's documents |
| `is_template_skeleton` | a placeholder inside a scaffolding template (`${{ values.* }}`), not a real entity |
| `source_repo`, `source_repo_basis` | the repo the entity describes, and how that was decided (the basis names the tool's evidence, e.g. `annotation:github.com/project-slug`, or `file_location`); null for repo-less entities such as domains |
| `repo_signals` | the evidence, as repo names: `slug` (an explicit owner/name reference), `source_location`, `links` |
| `part_of` | refs of the entities this one belongs to (system, domain, owner, parent) |
| `entity` | the descriptor document as written (key order kept) |

## Completeness

`org/verification.json` lists every default-branch commit the code host attributes to the account
(GitHub: commit search, via any verified email) that is missing from this dataset:
`attributed_commits_missing_from_dataset` counts them, out of `host_attributed_commits`. An empty
`missing` list means the identity configuration caught everything the host knows about.

Not covered:
- Repos the account cannot see, or deleted repos; repos never migrated to the current host.
- Commits that only ever existed on branches deleted without a PR, or force-pushed away.
- Commits by agents (e.g. Claude Code on the web, `claude/*` branches) that neither name the user nor
  sit in a PR the user authored: nothing in git ties them to the user.
- Reviews of other people's PRs, and issue/PR comments.
